# Dev-инстанс YouTrack

Инстанс, с которого `make openapi` модуля [youtrack](https://github.com/hakastein/youtrack) снимает спецификацию и на котором руками проверяют `ytrack` и измеряют факты
о сервере для ADR: русскоязычный
YouTrack с проектом `DEV`, на котором заведены кастом-поля всех типов, и проектом
`DOCS` с выключенным учётом времени.

```bash
make install
```

Одна цель проверяет типы, поднимает том, проходит мастер настройки и сидирует дев-инстанс. Дальше
инстанс живёт на <http://localhost:8091>, логин `admin`, пароль из `.env`.

Перед первым запуском — `cp .env.example .env` и `id -u`/`id -g` в `UID`/`GID`.

## Всё делается через docker

На хосте нет ни node, ни playwright: `src/wizard.ts` и `src/seed.ts` запускаются
только в контейнере `tools`, и цели `make` зовут их именно там. Транспайлера нет
— типы снимает сам node 24, а `tsconfig.json` держит `erasableSyntaxOnly`, чтобы
в код не попал синтаксис, который так не снимается. Снимает он их без проверки, поэтому `make install` и `make seed`
сначала гоняют `tsc` и при ошибке типов до инстанса не доходят.

| Цель | Что делает |
|---|---|
| `make install` | проверка типов и вся процедура с нуля |
| `make reset` | снести том и токены; дальше `make install` |
| `make up` / `make down` | поднять / погасить стек |
| `make wizard` | только мастер настройки |
| `make seed` | проверка типов и сидирование |
| `make typecheck` | `tsc` по `tools/src`, без выпуска кода |
| `make logs` / `make ps` / `make sh` | лог, состояние, оболочка в `tools` |

## Что здесь решено

**Образ — `jetbrains/youtrack` с Docker Hub, запиненный на `2026.1.13757`.** Факты о сервере в ADR
измерены на этой сборке. Работает он на встроенной бесплатной лицензии на десять
пользователей, а их тут трое.

**Тома именованные, а не каталоги хоста.** YouTrack работает под uid 13001 и
прав смонтированного каталога не меняет, так что bind-mount пришлось бы
готовить через `sudo`. Именованный том Docker создаёт из образа вместе с его
владельцем, и подготовки не требуется.

**Язык — русский.** `localizedName` есть только на локализованном инстансе: на
английском половина полей дев-инстанса стала бы непроверяемой.

**Мастер настройки проходится Playwright.** До первого токена у YouTrack нет
API вовсе — ни мастера, ни создания токена: Hub REST на сессию браузера отвечает
как гостю. Поэтому `src/wizard.ts` доводит дело до постоянного токена и кладёт
его в `.state/admin-token`, а всё остальное делает `src/seed.ts` по REST.

## Что на дев-инстансе

Проект `DEV`, 28 полей, покрывающих все 20 типов каталога
`/api/admin/customFieldSettings/types`. Двадцать восьмое — `Затраченное время`: без
него на DEV не включить учёт времени с затраченным временем. Среди значений бандлов
есть `Нужен реквеcт на выпуск` с латинской `c`.

Что дев-инстанс покрывает:

| Требование | Чем закрыто |
|---|---|
| все 20 типов полей | `tools/src/fields.ts`, проверяется на старте сидирования |
| поле, которого нет на задаче | `Причина отклонения` под условием `State = Отклонена` |
| поле с `canBeEmpty: false` | шесть: пять обязательных — `Type`, `Priority`, `Категория`, `Клиент` и `Модуль системы`, — и `Причина отклонения`, обязательная под условием `State = Отклонена`; обязательность сверяется по ответу привязки (`field_required_mismatch`), а под условием — по ответу флага (`required_condition_mismatch`) |
| поле с `localizedName` | `State`, `Type`, `Priority`, `Assignee`, `Subsystem`, `Fixed in build` |
| бандл с архивными значениями | `Плановый спринт` — 4 архивных из 6 |
| значение с пробелом и точкой | `Инфраструктура. DevOps` |
| period-поле | `Оценка` |
| второй токен с урезанными правами | `dev.limited`, токен в `.state/limited-token` |

Восемь задач и пять связей — `tools/src/content.ts`. DEV-1 и DEV-2 — задачи для
условного поля: `Причина отклонения` есть только у отклонённой DEV-2. DEV-2…DEV-6 —
целевые задачи связей DEV-1, по одной на тип: под одной задачей записи `IssueLink` разных типов при
проверке не различить.

| Откуда | Фраза | Куда | Направление у DEV-1 |
|---|---|---|---|
| DEV-1 | `relates to` | DEV-2 | `BOTH` |
| DEV-1 | `depends on` | DEV-3 | `INWARD` |
| DEV-1 | `subtask of` | DEV-4 | `INWARD` |
| DEV-1 | `is duplicated by` | DEV-5 | `OUTWARD` |
| DEV-1 | `Скопирована в` | DEV-6 | `OUTWARD` |

Учёт времени на DEV включён: оценка — `Оценка`, затраченное время —
`Затраченное время`, типов работ ровно пятнадцать, в порядке таблицы. Глобальный
каталог — эти пятнадцать, `ИИРазработка`, которая к DEV не привязана, и `Реализация`
мастера. У DEV-1 одна запись
времени: 90 минут типа `Разработка`. У DEV-4 записей нет, но `Затраченное время` у неё те же
90 минут: DEV-1 — её подзадача.

Статей у DEV две: `DEV-A-1` и вложенная в неё `DEV-A-2`. Дерево задано одной константой
из родителя и ребёнка, поэтому без ребёнка его не собрать.

Описание DEV-1 — враждебный многострочный текст: строка с хвостовыми пробелами посреди текста, строки
ровно `---` и ровно `~~~`, символ вне BMP, и перевода строки в конце нет — это тоже случай,
а не упущение. Описание DEV-3 начинается пустой строкой, DEV-4 — ведущим пробелом, DEV-5 —
пустой строкой, за которой идёт строка с ведущим пробелом: первой строкой эти случаи друг
друга исключают. Черты перечислены у задач отдельно от частей описания, и выпавшая черта
валит сидирование на старте. У DEV-1 одно вложение, `заметка-полигона.txt` — небольшой
текст в UTF-8, — и один комментарий.

Что покрывают связи, учёт времени, статьи и описания:

| Требование | Чем закрыто |
|---|---|
| связи всех пяти типов | таблица связей; фраза без типа (`links_unknown`) и тип без связи (`links_uncovered`) валят сидирование на старте, а направление каждой связи сверяется по `IssueLink` целевой задачи в ответе записи (`link_direction_mismatch`) |
| пятый, свой тип связи | `Copy` заводится до проекта с заданными свойствами и сверяется с ними (`link_type_mismatch`) |
| учёт времени с оценкой и затраченным временем | предопределённые прототипы, среди них `Оценка` и `Затраченное время`, резолвятся одним запросом до проекта (`prototype_missing`); включение, набор и порядок типов DEV сверяются по ответу записи (`time_tracking_mismatch`) |
| свой каталог типов работ | каталог доводится до таблицы до проекта: тип мастера, которого нет, — `work_item_type_missing`, тип инстанса вне таблицы — `work_item_types_uncovered`, расхождение по `autoAttached` — `work_item_type_mismatch` |
| запись времени у задачи | DEV-1; минуты, тип, текст и дата сверяются по ответу записи (`work_item_mismatch`) |
| дерево статей | родитель и ребёнок; ребёнок создаётся сразу с `parentArticle`, и родитель сверяется по ответу записи (`article_mismatch`) |
| вложение и комментарий у задачи | DEV-1; имя и размер вложения, текст комментария сверяются по ответу записи (`attachment_mismatch`, `comment_mismatch`) |
| описание с хвостовыми пробелами, `---`, `~~~` и символом вне BMP | DEV-1; ещё три случая первой строки — у DEV-3…DEV-5. Выпавшая из описания черта валит сидирование на старте (`text_feature_missing`), а каждое описание сверяется с ответом создания байт в байт (`description_mismatch`) |

Таблицы дев-инстанса ссылаются друг на друга, и рассогласование валит сидирование на старте, до
первой записи: задача, которой нет в `ISSUES`, — `issue_unlisted`, поле учёта времени вне
`FIELDS` — `time_tracking_field_unlisted`, тип записи времени вне набора DEV —
`work_item_type_unlisted`, одно имя поля с разными типами в таблицах проектов — `prototype_type_conflict`: прототип у
имени поля один на все проекты. Строку для каждого типа поля в таблицах по типу — бандл, тип проектного поля и поля
задачи, ключ и вид значения — требует tsc: без неё не проходит `make typecheck`, а `make install` и `make seed`, которые
начинают с проверки типов, останавливаются раньше инстанса.

Умолчания DEV: `State` необязательное с умолчанием `Новая`, `Priority` обязательное с умолчанием `Low`.
`Причина отклонения` обязательна, пока видна: других полей под условием у дев-инстанса нет. DEV-2 заведена отклонённой раньше, чем выставлена обязательность, и
остаётся без причины. У значения `Ядро` поля `Subsystem` владелец — `admin`: задаче с `Ядро` без `Assignee`
воркфлоу `Subsystem Assignee` ставит `admin` исполнителем.

Второй пользователь — `dev.member`, «Участник»: почта `dev.member@ytrack.local` подтверждена, пояс профиля —
`Asia/Vladivostok`, токен — в `.state/member-token`. К DEV его пускает глобальная роль `contributor`, а не команда:
проект у Hub один, `GLBL`, а в команду через REST входит только группа, и её пользователи попадают в `Assignee`.
Роль выдана пользователю, так что его группа `Участники полигона` прав не несёт. Пояс инстанса и профиль admin —
`Europe/Moscow`: на поясе admin стоит дата записи времени DEV-1.

DEV-7 — задача с историей правок: DEV-1…DEV-6 заняты другими измерениями, и история живёт на новой
задаче. Заголовок, описание и текст комментария admin на ней правлены по разу, личный тег admin `история-полигона`
навешен и снят, и каждая правка — свой запрос. Снятый тег остаётся на инстансе: удалённый, он унёс бы из истории свои
записи `TagsCategory`. Комментарий `dev.member` с `+1` дал его голос через воркфлоу `One Vote Comment`, а его запись
времени на 30 минут отправлена моментом 15:00 UTC 1 сентября и хранится 2 сентября — днём этого момента во
Владивостоке. Голос и дата записи здесь — образцы для чтения: пишущие измерения делаются на своих задачах.

DEV-8 — задача со значениями всех 20 типов полей. У DEV-1…DEV-6 непусты только четыре строки таблицы типов — enum 1,
enum \*, state и period, — а их значения заняты другими измерениями, поэтому остальные шестнадцать
живут на новой задаче. Непустых полей у DEV-8 23, и 22 из них пишет таблица: те же `Type`, `Priority`, `Категория`,
`Клиент` и `Модуль системы`, что у DEV-1, `State = Новая`, `Релиз` и `Плановый спринт`, `Fixed in build` и `Сборки`,
`Subsystem` и `Подсистемы`, `dev.member` в `Соисполнители`, `DEVELOPMENT Team` и `Участники полигона` в группах, дата,
дата-время с миллисекундами, целое, дробное, строка, двухстрочное `Примечание` и `Оценка` на 90 минут. Двадцать третье,
`Assignee`, ставит воркфлоу `Subsystem Assignee` — `admin`, владельца `Ядро`. `Система`, `Статус разработки`,
`Статус анализа` и `Затраченное время` у DEV-8 пусты, а `Причины отклонения` при `State = Новая` на ней нет.

DOCS — проект с выключенным учётом времени. Полей у DOCS четыре: обязательные `Priority` (`Critical`, `Blocked`, `Medium`, `Low`, умолчание `Low`) и `State`
(`To do`, `In Progress` и решённое `Done`, умолчание `To do`), а ещё `Assignee` и `Due Date`. Все четыре — прототипы,
которые инстанс заводит сам. Учёт выключен, но набор типов работ у проекта есть: пятнадцать типов DEV в
том же порядке и последним `ИИРазработка`. DOCS-1 заведена одним заголовком, `Priority` и `State` ей ставят умолчания, а
запись времени в неё сервер отвергает `403`.

Порядок полей DEV и DOCS — `ordinal` проектных полей, заданный в `tools/src/fields.ts`. У DEV первыми идут двадцать
полей — `Type`,
`Priority`, `Категория`, `Клиент`, `Модуль системы`, `Система`, `Assignee`, `State`, `Причина отклонения`,
`Соисполнители`, `Статус анализа`, `Плановый спринт`, `Порядок реализации`, `Плановая дата решения`, `Релиз`,
`Статус разработки`, `Затраченное время`, `Оценка`, `Дата начала работы`, `Внешний номер`, — а за ними восемь полей,
добранных ради недостающих типов, в порядке таблицы полей: `Subsystem`, `Подсистемы`, `Fixed in build`, `Сборки`,
`Группа доступа`, `Группы доступа`, `Коэффициент`, `Примечание`. У DOCS — `State`, `Priority`,
`Assignee`, `Due Date`. `ordinal` поля — его место в этом порядке, с единицы: у DEV от 1 до 28, у DOCS от 1 до 4.

Что покрывают умолчания, пользователи, история и порядок полей:

| Требование | Чем закрыто |
|---|---|
| необязательное поле с умолчанием | `State` → `Новая`; таблица полей DEV без необязательного поля с умолчанием (`optional_default_missing`) и умолчание не из бандла своего поля (`default_value_unlisted`) валят сидирование на старте; записанное умолчание сверяется по ответу записи (`field_default_mismatch`), а необязательность — по ответу привязки (`field_required_mismatch`), и `field_defaults` печатает её оттуда |
| обязательное поле с умолчанием | `Priority` → `Low`; таблица полей DEV без обязательного поля с умолчанием (`required_default_missing`) валит сидирование на старте, остальное — теми же `default_value_unlisted`, `field_default_mismatch` и `field_required_mismatch` |
| поле, обязательное под условием | `Причина отклонения` при `State = Отклонена`; таблица полей DEV без поля, обязательного под условием (`required_condition_missing`), и признак у поля любого проекта без условия (`required_condition_unlisted`) валят сидирование на старте, а обязательность ставится последними записями своего проекта — у DEV после порядка полей — и сверяется вместе с условием по ответу записи (`required_condition_mismatch`) |
| значение `Subsystem` с владельцем | `Ядро` → `admin`; владелец значения — только admin: поля привязываются раньше, чем заводятся остальные пользователи дев-инстанса. Другой владелец у поля любого проекта (`owner_unlisted`) и воркфлоу `Subsystem Assignee` вне каталога (`workflow_missing`) валят сидирование на старте, владелец сверяется по ответу записи (`owner_mismatch`), а использование воркфлоу на DEV — после привязки полей (`workflow_broken`) |
| `dev.limited` по-прежнему без ролей | после DOCS прямые роли Hub у `dev.limited` читаются токеном admin, и роль у него валит сидирование (`limited_role_granted`); роль, выданную группе, прямые роли не показывают, поэтому его собственный токен читает `/api/admin/projects`, и непустой список — тоже ошибка (`limited_projects_visible`); строка `users` печатает прочитанные роли и проекты |
| второй пользователь — не админ, с почтой и ролью | `dev.member` с подтверждённой почтой, глобальной ролью `contributor` и группой `Участники полигона`; роль или проект `GLBL`, которых нет в Hub, валят сидирование на старте (`member_role_missing`); логин и почта сверяются по `/api/users/me` его токеном (`member_mismatch`), группа — по ответу записи (`member_group_mismatch`) и по `/api/groups` (`member_group_missing`), роль — по ответу записи (`member_role_mismatch`) и по кэшу прав: без `READ_ISSUE` через минуту — `member_role_not_applied`, с правкой чужого комментария или чтением групп — `member_role_mismatch` |
| токен второго пользователя | `.state/member-token` — постоянный токен со scope YouTrack, как у `dev.limited` |
| пояс инстанса отличается от пояса профиля пользователя | инстанс и admin — `Europe/Moscow`, `dev.member` — `Asia/Vladivostok`; другой пояс инстанса или профиля admin (`time_zone_mismatch`) и пояс участника, равный поясу инстанса (`time_zone_fixture_inert`), валят сидирование на старте, а пояс участника сверяется по ответу записи (`profile_time_zone_mismatch`) |
| история правок заголовка, описания, тегов и текста комментария | DEV-7: заголовок, описание и текст комментария admin правлены по разу, тег навешен и снят; таблица без одной из этих пяти правок (`history_uncovered`) или с правкой, не меняющей значения (`history_edit_inert`), валит сидирование на старте; каждая правка сверяется по ответу записи (`summary_mismatch`, `description_mismatch`, `tag_mismatch`, `comment_mismatch`), а история — по `/api/activities`: записи самого сидирования точным числом, голос — включением (`history_mismatch`); вид правки перечислен один раз, и без ветки записи или ожидаемых записей истории он не проходит `make typecheck`, с которого начинаются `make install` и `make seed`, а запрос истории называет ровно те категории, которые сверяются |

## Что измерено на этом инстансе

- Поле отсутствует на задаче тогда и только тогда, когда у проектного поля стоит
  `condition` типа `FieldBasedCondition`.
- Бандл в теле привязки поля к проекту обязан нести `$type`. Без него — `500
  java.lang.InstantiationException`, без единого слова о причине.
- Предопределённый прототип тянет значение по умолчанию из штатного бандла, и
  свой бандл отвергается тем, что его не содержит: нужен `defaultValues: []`.
- Прототип `Due Date` («Срок», тип `date`) чистый инстанс заводит сам, но ни к одному проекту не привязывает, так что
  у DOCS все четыре поля — предопределённые.
- Умолчание пишется в уже привязанное поле: `POST /api/admin/projects/{id}/customFields/{поле}` с
  `{defaultValues: [{id, $type}]}`, значение — из ответа привязки. Без `$type` у значения — тот же `500
  java.lang.InstantiationException`, что и у бандла. Задача, созданная без `Priority` и `State`, приходит
  с `Low` и `Новая`: умолчание подставляется и в обязательное поле, и в необязательное.
- Значение с владельцем создаётся `POST /api/admin/customFieldSettings/bundles/ownedField/{бандл}/values`
  с `{name, owner: {id}}`, без `$type` у владельца, и отвечает `owner` с логином. У значения без владельца
  `owner: null`.
- Воркфлоу `Subsystem Assignee` привязывается к проекту из `POST /api/admin/projects` сам, и использование
  не сломано. Удаление восьми полей по умолчанию его ломает — `isBroken: true`, — привязка одного
  `Subsystem` не чинит, а с привязанным `Assignee` оно сразу снова `false`. Поэтому использование
  сверяется после привязки полей. Задача с `Subsystem = Ядро` без `Assignee` приходит с `Assignee: admin`
  уже в ответе создания.
- На DOCS, где `Subsystem` нет, использование `Subsystem Assignee` — `isBroken: true`, а `One Vote Comment` не сломан.
  Поэтому список воркфлоу, использование которых сверяется, у каждого проекта свой, и у DOCS он пуст.
- Обязательность под условием — тот же `canBeEmpty: false` у поля с `FieldBasedCondition`, и запись
  `{canBeEmpty: false}` условие не снимает. Задачу в `Отклонена` без причины сервер не создаёт: `400`,
  `error: "Field required"`, «Поле Причина отклонения обязательно», `error_type: workflow`,
  `error_rule_name: @jetbrains/required-custom-fields-feature`. Тем же ответом отвергается правка,
  переводящая задачу в `Отклонена` без причины. У задачи в `Новая` поля нет вовсе, и создание проходит.
- Задача, у которой условие выполнилось до флага, остаётся записываемой: комментарий, заголовок, описание,
  связь и тег отвечают `200`.
- Отклонённое создание съедает номер: в ответе `400` есть `error_issue_id`, и на дев-инстансе из шести задач отвергнутая
  задача заняла DEV-7 — созданная следом стала DEV-8, а `DEV-7` отвечал `404`.
- Токену без прав `/api/admin/projects` отвечает `200` и пустым списком, а
  `/api/admin/projects/{id}` — `404`. Ни одного `403`: «нет прав» и «нет
  проектов» по коду ответа неразличимы.
- Пользователь Hub становится пользователем YouTrack лениво. Сразу после `POST /hub/api/rest/users`
  `/api/users/{логин}` отвечает `404`, а первый же запрос его токеном — `/api/users/me` — `200` с логином и
  почтой, и после него находится и `/api/users/{логин}`.
- Почту права не скрывают: `/api/users` отдаёт её строкой и admin, и `dev.limited` без ролей, и участнику.
  `email: null` у admin — почта не задана, а не скрыта: так же она приходит и его собственным токеном.
- Группа заводится в Hub: `POST /hub/api/rest/usergroups` с `{name}`, пользователь в неё — `POST
  /hub/api/rest/usergroups/{id}/users` с `{id}` пользователя Hub, и ответ — сам пользователь. В `/api/groups`
  группа появляется через полсекунды, сразу с `usersCount: 1` и `$type` `NestedGroup`.
- Проект у Hub один — `GLBL` с id `0`, а `ringId` у проектов YouTrack нет, так что роль ставится на весь
  инстанс: `POST /hub/api/rest/users/{id}/projectroles` с `{role: {id}, project: {id}}`. Действует она не сразу:
  `/api/permissions/cache` токеном участника около пяти секунд отдаёт три права `jetbrains.jetpass`, а затем
  разом 28 прав `contributor`. Среди них `READ_ISSUE`, `CREATE_COMMENT` и `CREATE_WORK_ITEM`, но нет
  `UPDATE_NOT_OWN_COMMENT` и `jetbrains.jetpass.group-read`.
- Прямые роли пользователя — `projectRoles` в `/hub/api/rest/users/{id}`: у admin `system-admin`, у `dev.member`
  `contributor`, а у `dev.limited` ключа в ответе нет вовсе — пустой список Hub не отдаёт. `transitiveProjectRoles`
  добавляет роли групп: у всех троих `observer` на `GLBL` от группы «Зарегистрированные пользователи», и
  `sourcedProjectRoles` помечает её источник `groupProjectRoleSource`, а свою роль — `ownRoleSource`. Токену
  `dev.limited` `/api/admin/projects` при этом отвечает `[]`: `observer` на `GLBL` проектов YouTrack не открывает.
- `/api/groups` участнику — `403 {"error":"Forbidden","error_description":"HTTP 403 Forbidden"}`: из ролей Hub
  `jetbrains.jetpass.group-read` есть только у `system-admin`.
- Настройки учёта участник видит: `plugins` DEV приходят через `/api/admin/projects/DEV`, через
  `…/timeTrackingSettings` и через `project(plugins(…))` задачи — `enabled: true` и пятнадцать типов. А
  `/api/admin/projects/DEV/customFields` отвечает ему `200 []`: полей для него нет, но и ошибки нет.
- Массив `customFields` проекта идёт в порядке `id` проектных полей, а `id` у полей разных классов — из разных серий:
  у DEV `Assignee` (`181-2`) стоит после `Сборки` (`180-29`), хотя привязан раньше. Настроенный
  порядок — `ordinal`, и привязанное через REST поле приходит с `ordinal: 0`.
- `ordinal` пишется в привязанное поле: `POST /api/admin/projects/{id}/customFields/{поле}` с `{ordinal}` отвечает `200`
  с записанным значением, и так же оно читается. Соседей запись не сдвигает, повтор значения сервер принимает,
  `canBeEmpty` и `defaultValues` остаются прежними, а массив `customFields` проекта — в порядке `id`. Поэтому `ordinal`
  дев-инстанса — с единицы: запись нуля в поле, где ноль уже стоит, сверка по ответу не отличила бы от пропущенной.
- Порядок полей участнику виден только с задачи. `project(customFields)` у неё ему тоже `[]`, а `customFields` задачи
  приходят все, и у каждого `projectCustomField` с `id` и `ordinal` — теми же, что токеном admin.
- Массив `customFields` задачи идёт не по `ordinal` проектного поля, а по `ordinal` прототипа из
  `/api/admin/customFieldSettings/customFields`. У восьми прототипов, которые инстанс заводит первыми, — от `Priority`
  до `Fixed in build` — он от 0 до 7, а у `Due Date` и всех следующих — 8, и внутри восьмёрки порядок массива не
  следует ни `id`, ни `ordinal` проектного поля. Поэтому у DEV-8 первыми приходят `Priority`, `Type`, `State` и
  `Assignee`.
- В команду проекта через REST входит только группа: `POST /api/admin/projects/{id}/team/groups` с `{id}` —
  `200`, и её пользователи попадают и в команду, и в `aggregatedUsers` у `Assignee`. Одного пользователя так не
  добавить: `POST …/team/users` с `{id}`, `PUT …/team/users` и `POST /api/groups/{команда}/users` — `405`,
  `POST …/team/users/{id}` — `404`, а `POST …/team` с `{users}` и `POST /api/admin/projects/{id}` с `{team}`
  отвечают `200` и ничего не меняют. Глобальная роль ни команды DEV, ни `aggregatedUsers` у `Assignee` не трогает.
- Размер лицензии через REST не читается: у `License` в спеке только `username`, `license` и `error`, а
  `/hub/api/rest/licenses` отвечает `404`.
- Чистый инстанс заводит четыре типа связей — `Relates`, `Depend`, `Duplicate`,
  `Subtask`. Пятый, `Copy`, заводит сидирование, и все девять его свойств
  инстанс вернул дословно. `aggregation: true` и
  `localizedTargetToSource: ""` взяты из тела записи — без них там `false` и `null`.
  `localizedName: null` и `localizedSourceToTarget: null` совпадают с умолчанием.
  `readOnly` из тела не пишется — `true` приходит `false`.
- Второй тип с тем же именем — `400 invalid_properties`, поэтому уже заведённый тип
  сверяется, а не заводится заново.
- Записей `IssueLink` у задачи по одной на ненаправленный тип и по две на направленный, с пятым
  типом девять. У `Relates` запись `163-0`, `BOTH`, без суффикса; у направленных
  суффикс `s` — `OUTWARD` с фразой `sourceToTarget`, `t` — `INWARD` с
  `targetToSource`. Заведённый тип получил `163-4` и записи `163-4s`/`163-4t`.
- Связь пишется `POST /api/issues/{задача}/links/{IssueLink}/issues` с телом `{id}`
  целевой задачи, без `$type`, и отвечает самой целевой задачей. Обратная сторона
  появляется у целевой задачи сама, в записи `IssueLink` противоположного направления.
- Воркфлоу `Duplicates` и `Subtasks` на DEV помечены `isBroken: true`, но `Duplicates`
  исполняется. Задачу в `Duplicate` без связи `duplicates` он не даёт создать
  (`400`, правило `issue-in-duplicate-state-must-have-duplicates-link`), а связь
  `is duplicated by` сам переводит дубль в `Duplicate`. Поэтому DEV-5 создаётся в
  `Новая`. Приоритет DEV-1 при этом не растёт, а связь `Subtask` состояний не двигает.
- Мастер заводит пять типов работ: `Разработка`, `Тестирование`, `Документирование` с
  `autoAttached: true`, `Исследование` и `Реализация` с `false`. `Реализация` к DEV не
  привязывается, но на неё записано время в DEMO, поэтому из каталога она не удаляется. Остальные двенадцать сидирование
  заводит `POST /api/admin/timeTrackingSettings/workItemTypes` с `{name, autoAttached}`;
  второй тип с тем же именем — `400 invalid_properties`.
- `autoAttached` через REST не действует ни в одну сторону. Проект из `POST
  /api/admin/projects` получает весь глобальный каталог, типы с `false` тоже, а новый
  тип не появляется у уже созданных проектов даже с `true`.
- Набор типов проекта пишется целиком: `workItemTypes: [{id}]` в `POST
  /api/admin/projects/{id}/timeTrackingSettings` заменяет его, и ответ несёт новый
  набор. Тем же POST включается учёт — `{enabled: true, estimate: {id, $type},
  timeSpent: {id, $type}}` со ссылками на проектные поля. Поштучно тип тоже
  отвязывается и привязывается: `DELETE …/timeTrackingSettings/workItemTypes/{id}` —
  `200` с пустым телом, повтор — `404`; `POST …/timeTrackingSettings/workItemTypes`
  принимает только `{id}` (одно `name` — `400`), повтор — `200` без дубля.
- Порядка в наборе типов сервер не хранит: перестановка `178-2, 178-0, 178-4, 178-1, 178-3`
  в теле на DEMO вернулась и ответом, и GET-ом как `178-0`…`178-4`, в порядке глобального
  каталога, а порядкового поля у `WorkItemType` в спеке нет. Порядок DEV совпадает с таблицей
  оттого, что недостающие типы заводятся в порядке таблицы вслед за четырьмя мастера.
- Время типом, не привязанным к проекту, не записать: `400 invalid_properties`,
  «Выбранный тип работы не поддерживается в этом проекте YouTrack».
- Проект из `POST /api/admin/projects` приходит с выключенным учётом, но со всем каталогом типов работ — семнадцатью.
  Набор пишется и при выключенном учёте: `POST …/timeTrackingSettings` с `{enabled: false, workItemTypes: [{id}]}` отвечает
  `200` с `enabled: false`, `estimate` и `timeSpent` — `null`, и типы приходят в порядке глобального каталога.
- Запись времени в задачу проекта с выключенным учётом сервер отвергает и токеном admin:
  `403 {"error":"Forbidden","error_description":"HTTP 403 Forbidden"}` — тот же ответ, что на нехватку прав. Записей у
  задачи после отклонения нет.
- Запись времени — `POST /api/issues/{id}/timeTracking/workItems` с `{duration:
  {minutes}, type: {id}, text, date}`, тип только по `id`. Длительность — только
  минутами: с одним ISO-`id` запись отвергается как запись без длительности (`400`), а
  `presentation` сервер разбирает сам (`"3ч"` — 180 минут). `date` — полночь UTC в
  миллисекундах, приходит как отправлена.
- Запись двигает `Затраченное время` каскадом, и сдвинутое поле приходит уже в ответе самой
  записи, если спросить `issue(customFields(...))`: у DEV-1 там `{id: "PT1H30M", minutes: 90,
  presentation: "1ч 30м"}`, у самой записи — `{id: "90", minutes: 90, presentation: "1ч 30м"}`.
- Каскад не кончается задачей записи: `Затраченное время` поднимается к родителю по `Subtask`.
  У DEV-4 записей времени нет, а в поле 90 минут — запись её подзадачи DEV-1. В DEMO так же:
  у DEMO-5 записей нет, а в поле 330 минут — записи подзадачи DEMO-8 на 120 и 210. Без
  подзадач с записями поле — сумма своих записей (DEMO-1 — 150 из 60, 60 и 30; DEMO-3 — 480),
  а без записей вовсе — `null`, не ноль. Задачи, у которой есть и свои записи, и записи
  подзадач, и подзадач в два уровня с записями на инстансе нет: их сложение не измерено.
- Мастер заводит в DEMO статью `DEMO-A-1`, без родителя и детей.
- `project` у статьи в спеке помечен `readOnly`, но без него статья не создаётся: `400
  Article.project-is-invalid`, «Required field project of Article[…] is undefined».
- Статья пишется `POST /api/articles` с `{project: {id}, summary, content}`, без `$type`.
  Родитель встаёт при создании: `parentArticle: {id}` в том же теле. Ответ несёт
  `parentArticle`, а у родителя ребёнок появляется в `childArticles` сам, поэтому
  отдельный `POST /api/articles/{id}/childArticles` дев-инстансу не нужен.
- Несуществующего родителя сервер не отвергает: `200`, и статья создаётся корневой, с
  `parentArticle: null`. Поэтому родитель ребёнка сверяется по ответу записи.
- Описание сервер хранит байт в байт: ответ создания и последующее чтение возвращают
  хвостовые пробелы, строки `---` и `~~~`, символ вне BMP, отсутствие завершающего
  перевода строки, пустую первую строку, ведущий пробел в первой строке и их сочетание
  такими, какими они записаны. Не переносит он только CR: `\r\n` приходит `\n`, одиночный
  `\r` пропадает без замены. Поэтому случая с CR на дев-инстансе нет — сверка байт в байт на нём
  упала бы.
- Вложение задачи грузится multipart — `POST /api/issues/{id}/attachments` с частью
  `files[0]`, как в спеке, — и отвечает массивом вложений. Кириллическое имя файла приходит
  дословно, `size` — в байтах.
- `url` вложения относительный: `/api/files/<id>?sign=…&updated=…`. По подписанной ссылке
  файл отдаётся без авторизации — `200` и тот же размер. Без `sign` — `400` «Sign parameter
  is required», и токен в заголовке `sign` не заменяет.
- Комментарий пишется `POST /api/issues/{id}/comments` с `{text}`, без `$type`, и отвечает
  самим комментарием с текстом, как он записан.
- Заголовок и описание правятся `POST /api/issues/{id}` с `{summary}` или `{description}`, текст комментария —
  `POST /api/issues/{id}/comments/{комментарий}` с `{text}`. Тег из `POST /api/tags` с одним `{name}` — личный:
  владелец — тот, чей токен пишет, `visibleFor` и `updateableBy` — `null`. Навешивается тег
  `POST /api/issues/{id}/tags` с `{id}`, и ответ — сам тег, а снимается `DELETE /api/issues/{id}/tags/{тег}` —
  `200` с пустым телом.
- Запись истории видна в `/api/activities` сразу после правки, и у каждой из четырёх правок своя категория. У
  заголовка — `SummaryCategory` (`SimpleValueActivityItem`), у описания — `DescriptionCategory`
  (`TextMarkupActivityItem`): цель — `Issue`, `targetMember` — `summary` и `description`, `removed` и `added` —
  строки «было» и «стало». У тега — `TagsCategory` (`TagsActivityItem`), цель — `Issue`, `targetMember` — `tags`:
  навешивание — `added: [Tag]` и `removed: []`, снятие — наоборот. У текста комментария — `CommentTextCategory`
  (`TextMarkupActivityItem`), цель — `IssueComment`, `targetMember` — `text`, строки. `field` у всех четырёх —
  `PredefinedFilterField` с `id` `summary`, `description`, `tag` и `comment text`, а его `name` локализован:
  «заголовок», «описание», «тег», «текст комментария».
- Сам комментарий — отдельная запись `CommentsCategory` (`CommentActivityItem`) с `targetMember: null`, и её
  `added: [IssueComment]` несёт текущий текст, а не тот, с которым комментарий создан.
- Удалённый тег уносит из истории свои записи: после `DELETE /api/tags/{id}` у задачи, с которой он был снят,
  `TagsCategory` пуста.
- Правки не сливаются: две правки заголовка с интервалом 12 мс — две записи `SummaryCategory`. А одно тело с
  заголовком и описанием даёт две записи с одним `timestamp`, и в выдаче описание оказалось раньше заголовка.
- Голос за `+1` пишет две записи от имени голосующего: `TotalVotesCategory` (`SimpleValueActivityItem`) с
  `removed: 0` и `added: 1` и `VotersCategory` (`VotersActivityItem`) с `added: [User]`. `timestamp` у них тот же,
  что у записи его комментария, а в выдаче они идут раньше неё. `One Vote Comment` режет текст добавленного
  комментария выражением `/\s|,|;|\.|\?|!|\\/` и, найдя слово `+1`, голосует от имени `ctx.currentUser`. Голос виден
  сразу: `votes: 1`, `voters.hasVote` — `true` токеном голосующего и `false` токеном admin.
- Запись времени в истории — `WorkItemCategory` (`WorkItemActivityItem`): цель — сама запись, `field` —
  `WorkItemFilterField` «работа», `added: [IssueWorkItem]`.
- Дату записи времени переводит пояс профиля того, чей токен пишет, а не пояс инстанса и не `author` в теле. Момент
  15:00 UTC 1 сентября токеном `dev.member` (`Asia/Vladivostok`) хранится `1788307200000` — полночью UTC 2 сентября,
  и так уже в ответе записи. Токеном admin (`Europe/Moscow`) этот момент хранится 1 сентября, 22:00 UTC 31 августа —
  тоже 1 сентября, а с `author` участника в теле — снова 1 сентября: `author` у записи — участник, `creator` — admin.
- Значения всех типов пишутся одним `POST /api/issues`. `$type` элемента `customFields` — по типу поля и его
  множественности: `Single…` и `Multi…IssueCustomField` у enum, version, build, ownedField, user и group,
  `StateIssueCustomField`, `DateIssueCustomField`, `TextIssueCustomField` с `{text}`, `PeriodIssueCustomField` с
  `{minutes}` и `SimpleIssueCustomField` у даты-времени, целого, дробного и строки. Значение бандла и группа пишутся
  `{name}`, пользователь — `{login}`, без `$type` у самого значения. Ответ создания и последующее чтение совпадают;
  пустое множественное поле приходит `[]`, одиночное — `null`.
- Группа приходит с `$type` своего рода: `DEVELOPMENT Team` — `ProjectTeam`, `Все пользователи` — `AllUsersGroup`,
  группа Hub `Участники полигона` — `NestedGroup`. Текст приходит `{text}` с `$type` `TextFieldValue`, период —
  `PeriodValue` с `minutes` и локализованным `presentation`: «1ч 30м».
- Дата хранится полднем UTC того дня UTC, на который пришёлся записанный момент: 00:00, 01:00, 21:00, 22:00 и 23:30 UTC
  16 сентября хранятся `1789560000000`, хотя с 21:00 UTC в поясе admin уже 17 сентября. Пояс профиля пишущего день
  даты не сдвигает, в отличие от даты записи времени. Дата-время хранится до миллисекунды: `1788134400123` приходит как
  записано.
- `Fixed in build`, записанный при создании задачи в `Новая`, на ней остаётся: воркфлоу `Update Fixed in Build` на DEV
  не сломан, но это значение не очищает.
- Запись пользователя бандл не пополняет: `dev.member` записан в `Соисполнители` при пустом бандле, и у
  `DEVELOPMENT: Соисполнители` `aggregatedUsers`, `individuals` и `groups` так и остались пусты.
